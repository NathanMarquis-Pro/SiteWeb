My part: making the data usable

We started with 1,294,426 products and ended up with 548,913. I removed more than half of the catalogue, and I can justify every single row I dropped.

Each of my rules produces its own report with figures. The cleaning report builds itself, so the whole team can see what changed and why.

I then split the data into Parquet files with DuckDB and prepared the feature file for the upcoming models.

I don't make up missing nutrient values: I flag them. Filling them in now would bias the models; that has to happen after the train/test split.

Internship · iMSA, April to June 2025

From one unreadable test to 48 tests the whole team can maintain

My main project was automating the tests of an online service for the MSA (French agricultural social security) with Playwright. A similar project already existed in the company, but when I opened it, I couldn't make sense of it at all: the other teams didn't have the same needs as ours.

So I started again from the documentation. The first time my test turned green, I was amazed: Playwright moved around the page and clicked the buttons like a real user, only 200 times faster.

That's when the real thinking began: making these tests maintainable and easy to understand, because I would have to hand them over.

How I work

Three habits picked up during my degree, my internship and my training, which I keep on every project.

  • I check before I believe.

    You read everywhere that data preparation matters more than the algorithm. I tested it on a lab exercise: it's more nuanced, it depends on the model. See the Wine Quality exercise

  • I build things you can run again.

    My Parcoursup script downloads the official data, checks the file, builds the database and cleans up after itself. One run, the same result every time. See the project

  • I write for whoever takes over my code.

    Test tools designed for the whole team at iMSA, an automatic report for every cleaning rule in NutriScope. See the internship
